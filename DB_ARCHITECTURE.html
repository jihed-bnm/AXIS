1 Big Picture — Three Storage Layers

The system uses three distinct storage layers, each with a different purpose:

PostgreSQL — OLTP (Operational)

The live, transactional database. Every user action (creating a deal, sending an invoice) writes here in real time. Tables are normalised to avoid redundancy.

Engine: PostgreSQL 16  |  ORM: SQLAlchemy 2.0

PostgreSQL — OLAP (Warehouse)

A separate schema inside the same PostgreSQL instance, shaped as a star schema. Used for analytics and AI context. Populated by the ETL pipeline — never written by the app directly.

ChromaDB — Vector Store (RAG)

Stores text embeddings (768-dimensional vectors) of warehouse documents. The AI uses cosine similarity search here to find relevant context before answering questions. Persisted to ./chroma_db/ on disk.

2 SQLAlchemy — How the ORM Works

SQLAlchemy is a Python ORM (Object-Relational Mapper). Instead of writing raw SQL, we define Python classes that map to database tables. SQLAlchemy generates and executes the SQL automatically.

2.1 The Three Core Objects

ObjectWhat it isWhere it lives
engineThe connection pool to PostgreSQL. Reads the DATABASE_URL from the environment and manages the underlying psycopg2 connections.database.py
BaseThe declarative base. All model classes inherit from it. Calling Base.metadata.create_all() at startup creates every table that doesn't yet exist.database.py
SessionLocalA session factory. Each session is a unit-of-work: it tracks changes and flushes them to the DB in a transaction.database.py

2.2 Session Lifecycle — Two Patterns

get_session() — for Tools & Scripts

Returns a raw session. The caller must close it manually.

db = get_session()
try:
    result = db.query(Company).all()
    db.commit()
finally:
    db.close()  # always runs

Used inside every LangChain tool function.

get_db() — for FastAPI Routes

A generator (uses yield). FastAPI's Depends() system calls it, gets the session, then closes it automatically after the request finishes.

@app.post("/chat")
def chat(db = Depends(get_db)):
    ...
    # db closes after response

2.3 Defining a Table — Example

class Company(Base):
    __tablename__ = "companies"
    id       = Column(Integer, primary_key=True)
    name     = Column(String, nullable=False, index=True)
    industry = Column(String)
    status   = Column(String, default="prospect")  # prospect | client | inactive

    deals    = relationship("Deal", back_populates="company")

The relationship() call tells SQLAlchemy how to join tables. Accessing company.deals in Python automatically runs the correct JOIN — no SQL needed.

2.4 auto-create at Startup

In main.py, before the server starts accepting requests:

from backend.models.database import create_tables
create_tables()  # runs Base.metadata.create_all() → creates any missing tables

This is idempotent — it never drops existing tables, only creates missing ones.

3.3 Invoicing Tables (invoice_models.py)

TablePurposeKey Columns
invoices The main invoice document. Linked to a company and optionally a deal. id, invoice_number (unique), company_id (FK), deal_id (FK), status, subtotal, tax_rate (19% TVA), tax_amount, total (TND), issue_date, due_date, paid_at

Soft Delete Pattern: Tables like companies, contacts, deals, invoices have an is_deleted boolean column. Records are never physically removed — they are flagged. All queries filter WHERE is_deleted = false. This preserves historical data and the audit trail.
Currency: All monetary values are stored in TND (Tunisian Dinar). Tunisia's TVA rate is 19%, hardcoded as the default tax_rate on every invoice.

4 Data Warehouse — Star Schema (OLAP)

4.1 What is a Star Schema?

A star schema separates data into two types of tables:

  • Dimension tables — descriptive attributes (who, what, when, where). Prefixed dim_.
  • Fact tables — measurable events or transactions (how much, how many). Prefixed fact_.

Fact tables sit in the centre and reference dimension tables by surrogate keys. The resulting diagram looks like a star — hence the name.

4.2 Star Schema Diagram

4.5 Surrogate Keys vs Natural Keys

Why two key columns in dimension tables?

Each dimension has two identifiers:
  • client_key — surrogate key: auto-generated integer, used for all joins inside the warehouse. Stable even if source data changes.
  • source_id — natural key: the original companies.id from the operational DB. Used by the ETL to look up which warehouse row to update.
This pattern (surrogate + source) is standard data warehouse practice. The warehouse is isolated from operational ID changes.

4.6 Date Key Design

Instead of storing a DATE foreign key, the system uses an integer date key in the format YYYYMMDD:

def _date_key(d: date) -> int:
    return d.year * 10000 + d.month * 100 + d.day
# Example: 2024-03-15 → 20240315

This integer joins to dim_date.date_key. Benefits: fast integer join, human-readable, sortable without date parsing.

5 ETL Pipeline — From Operational Data to Warehouse

ETL = Extract, Transform, Load. The pipeline reads live operational data, cleans/restructures it, and loads it into the warehouse tables.

5.1 The Two ETL Processes

ETL 1 — CSV → Staging (etl_pipeline.py data ingestion part)

External data (e.g., data/staging/clean_invoices.csv) is ingested into operational tables. Used during initial setup and for bulk imports from legacy systems.

Flow: CSV file → pandas read → validate/clean → INSERT into operational tables

ETL 2 — Operational DB → Warehouse (etl_pipeline.py main ETL)

The main analytical ETL. Reads from live operational tables, computes derived metrics, and loads into the star schema. Run on-demand or via the Airflow DAG.

Flow: OLTP tables → transform → UPSERT/TRUNCATE-RELOAD into warehouse

5.2 ETL Execution Order — Dependency Chain

Dimensions must be loaded before facts because facts reference dimension surrogate keys:

1. dim_date → 2. dim_client → 3. dim_employee → 4. dim_service → 5. fact_revenue → 6. fact_deals → 7. fact_proj_perf → 8. fact_hr_events

If step 5 runs before step 2, the client_key lookup would fail — the warehouse rows don't exist yet.

5.3 Load Strategies

StrategyUsed ForHow it WorksWhy
Upsert Dimension tables (dim_client, dim_employee) Query by source_id. If row exists → UPDATE. If not → INSERT. Dimensions are slowly changing. We want to update names/status without losing history.
Truncate & Reload Fact tables (fact_revenue, fact_deals, etc.) DELETE FROM fact_x; then INSERT all rows fresh. Facts are fully derived from operational data. Simpler to rebuild than partial-update. Always consistent.
Insert-if-missing dim_date, dim_service Load existing keys into a Python set. Only insert rows not in that set. These tables rarely change. Avoid duplicates without a full DELETE.

5.4 Key Transform Logic

TransformWhereExample
Date → date_key integer _date_key() 2024-03-15 → 20240315
Quarter calculation _quarter(month) (month - 1) // 3 + 1 → March = Q1
Days to pay etl_fact_revenue() (paid_at - issue_date).days — NULL if not paid
Sales cycle etl_fact_deals() (closed_at - created_at).days — NULL if deal still open
Budget burn % etl_fact_projects() spent / budget * 100

Computed client totals etl_dim_clients() Queries live DB for SUM(invoice.total) and COUNT(won deals) per company, stores result in dim_client.total_revenue

5.5 Error Handling & Transaction Safety

db = get_session()
try:
    etl_dim_date(db)
    etl_dim_clients(db)
    etl_fact_revenue(db)
    ...
    db.commit()        # atomic: all steps succeed or nothing commits
except Exception as e:
    db.rollback()      # undo everything if any step fails
    raise
finally:
    db.close()         # connection always returned to pool

All ETL steps run inside a single transaction. If fact_revenue fails after dim_client succeeded, the rollback undoes everything — the warehouse stays consistent.

6 ChromaDB — Vector Store & RAG

6.1 What is RAG?

RAG (Retrieval-Augmented Generation) is a technique where the AI, before generating a response, first searches a knowledge base for relevant documents and includes them in its prompt as context. This lets the AI answer questions about specific company data without hallucinating.

User query: "What deals do we have with Tunisie Telecom?" │ ▼ [1] ERPRetriever.retrieve("Tunisie Telecom deals") │ → embed query using nomic-embed-text (768-dim vector) │ → cosine similarity search in ChromaDB jbm_crm collection │ → returns top-5 most relevant document chunks ▼ [2] Context injected into agent prompt: "[Context 1 - crm (relevance: 0.91)]: Deal: ERP migration, value 45,000 TND..." │ ▼ [3] LLM (qwen2.5:7b) answers using both the context AND tool calls

6.2 Embedding Setup

ComponentValue
Embedding modelnomic-embed-text via Ollama (runs locally)
Vector dimensions768
Distance metricCosine similarity (hnsw:space = cosine)
StorageLocal file: ./chroma_db/
Collectionsjbm_crm (companies, deals, activities)  |  jbm_invoicing (invoices)

6.3 What Gets Embedded?

Rule: Only warehouse tables (dim_* and fact_*) are embedded — never operational tables. This means RAG context is always derived from the clean, validated analytical snapshot, not raw live data.

The embedding pipeline (backend/rag/embedding_pipeline.py) reads from warehouse tables and converts records into human-readable text documents before embedding. Example:

# A dim_client row becomes a text document:
"Company: Tunisie Telecom | Industry: Telecom | City: Tunis
 Status: client | Total Revenue: 142,500 TND | Won Deals: 3"

6.4 Retrieval Process (ERPRetriever)

retriever = ERPRetriever(module="crm", top_k=5)
docs = retriever.retrieve("contract renewal Tunisie Telecom")
context = retriever.format_context(docs)
# context is a formatted string injected into the agent's system prompt

Steps internally:

  1. Convert query to a 768-dim embedding vector
  2. ChromaDB finds the n_results closest vectors by cosine distance
  3. Results are sorted by similarity score (1 − distance)
  4. Top-5 documents are returned as langchain.Document objects

6.5 Setting Up RAG

python -m backend.rag.setup_rag
# 1. Checks Ollama + nomic-embed-text is running
# 2. Runs full embedding pipeline (reads warehouse → embeds → writes to chroma_db)
# 3. Runs test query to confirm retrieval works
Important: The ETL must be run before RAG setup. The embedding pipeline reads warehouse tables — if they're empty, ChromaDB collections will be empty too, and the AI will have no context to draw from.

7 Audit Log — Every Write is Tracked

Every tool function that mutates data must call log_action() from backend/utils/audit.py after the mutation succeeds. This writes a row to the audit_logs table.

from backend.utils.audit import log_action

# Inside a confirmed write tool:
db.add(new_company)
db.commit()
log_action(db, action="CREATE", entity="company", entity_id=new_company.id,
           payload={"name": name, "industry": industry},
           result="success")

actionCREATE, UPDATE, DELETE, READ

8 Two-Phase Write Pattern

All mutating tools follow a two-step confirmation flow to prevent accidental writes:

User request → Tool called (confirmed=False) → Preview shown to user → User confirms → Tool called (confirmed=True) → DB write + AuditLog 
@tool
def create_company(name: str, industry: str, confirmed: bool = False) -> str:
    if not confirmed:
        return f"Preview: create company '{name}' in {industry}. Reply 'yes' to confirm."

    db = get_session()
    try:
        company = Company(name=name, industry=industry)
        db.add(company)
        db.commit()
        log_action(db, "CREATE", "company", company.id, {...}, "success")
        return f"Company '{name}' created (ID {company.id})."
    finally:
        db.close()

Defence Tip: If asked "why star schema instead of OLTP for analytics?"

OLTP tables are normalised (many joins needed). The star schema pre-computes joins and derived metrics (sales cycle, budget burn %, etc.) into flat fact tables. BI tools and the AI can query them with simple aggregations — no complex multi-table JOINs, much faster.
